# ADR 0002: Local accounts with JWT

Status: accepted. Date: 2026-10-04.

## Context
ADR 0001 left the choice between Firebase Auth and our own JWT open. The app needs sign-in on every route and strict separation of each user's data. It has no social login and no need for a second service.

## Decision
- Email and password accounts held in our own database.
- Passwords hashed with scrypt from Node's standard library, with a random salt per password. No hashing dependency to vet.
- A signed JWT access token (`@nestjs/jwt`), 7 days by default, sent as a bearer token.
- One global guard: every route needs a valid token unless marked `@Public()` (register, login, health). The guard also checks that the account still exists.
- Sign-in routes have a tighter rate limit than the rest of the API.
- Login gives the same answer for an unknown email and a wrong password.

## Trade-offs
- No refresh tokens, password reset or email verification. Acceptable for a demo; needed before real users.
- A token stays valid until it expires; there is no server-side sign-out list.
- The phone keeps the token in app preferences, not the hardware-backed keystore. Moving it to secure storage is a small follow-up.
- Firebase Auth would give reset and verification for free, at the cost of a second service, a project to configure and keys to manage.
